# AGENTS.md — WarpBuster Core

Этот файл содержит обязательные правила разработки для Codex и любых других coding agents.

## 1. Не реализовывать проект целиком

Работать **только над текущим milestone/task**.

Если задача из `tasks/003-...`, не реализовывать функциональность из `004+`, даже если это кажется удобным.

Разрешается:
- создать интерфейс/placeholder, необходимый текущему этапу;
- оставить TODO со ссылкой на будущий milestone.

Запрещается:
- «заодно» писать repair engine, routing, web API, OAuth и т. п.

## 2. Главный инвариант продукта

> Never modify plausible movement. Repair only demonstrably impossible GNSS data.

Отклонение от course не является доказательством ошибки.

Integrity Detector не должен использовать GPX course для классификации GPS/GNSS как corrupted.

## 3. Detection и Reconstruction — разные подсистемы

Pipeline:

FIT → normalize → Integrity Detector → corrupted intervals → optional Reconstruction

Course/OSM/DEM могут использоваться только на стадии Reconstruction.

## 4. Консервативность

При сомнении:
- предпочитать `UNKNOWN` / `MEDIUM` / `LOW`;
- не помечать физически правдоподобное движение corrupted;
- не выполнять auto-repair при низкой уверенности.

False positive опаснее false negative.

## 5. Timestamps по умолчанию неизменяемы

При GNSS repair:
- не изменять timestamps;
- не «лечить» невозможную скорость добавлением времени;
- считать clock trustworthy, пока нет независимого доказательства обратного.

## 6. FIT — главный формат

Не превращать FIT → GPX → FIT как основной pipeline.

Цель — максимально lossless работа с исходным FIT.

Неизвестные messages/fields/developer fields должны по возможности сохраняться.

## 7. Минимальные изменения

После repair менять только поля, зависимые от повреждённых координат и необходимые агрегаты.

В отчёте обязательно показывать FIT diff.

## 8. Никакого AI/LLM в core

Core должен быть:
- deterministic;
- offline;
- воспроизводимым;
- тестируемым.

## 9. Никаких magic numbers

Все thresholds detector-а должны находиться в конфигурационной модели, например `IntegrityConfig`.

Каждый threshold:
- имеет имя;
- единицы измерения;
- комментарий;
- default;
- тест.

## 10. Не привязываться к Garmin

Нормализованная модель активности vendor-neutral.

Garmin/COROS — источники FIT, а не разные алгоритмы детекции.

## 11. Производительность

Не реализовывать наивный полный O(n²) reachability для длинных треков.

Расширенный поиск запускать только вокруг подозрительных переходов либо использовать ограниченные окна/индексы.

Цель MVP: анализ ~20 000 records менее чем за 5 секунд на современном ноутбуке.

## 12. Тесты обязательны

Каждый milestone должен:
- добавлять/обновлять unit tests;
- не ломать предыдущие tests;
- иметь acceptance criteria из task-файла.

Нельзя завершать task с красными тестами.

## 13. Приватные реальные FIT

Пользовательские FIT-файлы не коммитить в публичный репозиторий.

Для них использовать, например:

`tests/private/`

и добавить директорию в `.gitignore`.

Публичные тесты должны использовать синтетические fixtures или явно разрешённые данные.

## 14. Не угадывать FIT semantics

Если значение FIT-поля или его происхождение неизвестно:
- не менять его;
- документировать неопределённость;
- не выдавать предположение за факт.

## 15. Перед кодом

Для каждого task сначала:
1. кратко сформулировать план;
2. перечислить файлы, которые будут затронуты;
3. назвать спорные решения;
4. затем писать код.

## 16. После кода

В финальном отчёте task-а указать:
- что реализовано;
- что сознательно не реализовано;
- какие тесты добавлены;
- команды проверки;
- известные ограничения;
- соответствует ли task acceptance criteria.
