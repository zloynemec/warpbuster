# WarpBuster Web

Отдельный веб-пакет для задачи [013](../tasks/013-web-processing-and-result-privacy.md).
Статические страницы находятся в `dist/`, Python-сервис — в `backend/warpbuster_web/`.
Сервис передаёт файлы в `warpbuster.pipeline.run_repair` и отображает его результат.
Последовательность обработки, политика и OSM-подготовка находятся в Core
([task 014](../tasks/014-shared-processing-pipeline.md)); вебу принадлежат HTTP,
очередь, ограничения развёртывания и публичная проекция отчёта.

В [023](../tasks/023-fit-only-web.md) добавлен FIT без GPX: одна форма,
публичные сведения о GPS-покрытии и возврат инициатора на форму при отказе.
Результаты Linux/browser acceptance зафиксированы в разделе 023C этой задачи.

Страница `/faq` (`dist/faq/index.html`) кратко описывает принцип сохранения данных,
восемь этапов обработки, хранение файлов, cookie и доступ по публичной ссылке.
Доступна без JavaScript с главной, страницы загрузки и результата. При изменении
сроков хранения, политики восстановления или публичных показателей обновляйте и FAQ.

## Локальный запуск

Из корня репозитория, в окружении Python 3.14:

```bash
.venv/bin/python -m pip install -e . -e 'web[dev]'
.venv/bin/python -m warpbuster_web
```

Открыть <http://127.0.0.1:8000/fix>. Используйте один и тот же адрес: cookie для
`localhost` и `127.0.0.1` различаются. Сервер слушает только loopback по умолчанию.
Статический `python -m http.server` подходит для просмотра вёрстки, но не для обработки.

Для восстановления по OSM нужен Linux: на macOS запускайте сервис в Docker
(раздел «Контейнер» ниже). Нативный macOS-сервер позволяет проверять интерфейс
и GPX-сценарий, но изолированный OSM worker возвращает `isolation_unavailable`.
Это ограничение платформы runtime; отключать isolation для обхода не следует.

Один процесс сервера обслуживает страницы, API и устойчивую очередь SQLite.
Один фоновый worker последовательно запускает отдельный Python-процесс на задание.
Файловая блокировка предотвращает запуск двух worker для одной директории данных.
Не использовать несколько Uvicorn workers. При перезапуске очередь сохраняется;
прерванные загрузки/обработки получают понятную ошибку. Неполные загрузки удаляются,
а полностью принятая пара сохраняется даже после прерванной обработки.

## Сценарий и доступ

1. `/fix` создаёт анонимную сессию и принимает обязательный FIT активности и
   необязательный GPX маршрута. Оба блока сразу видны и одинаково заметны.
   GPX значительно помогает восстановлению; запуск доступен и без него.
   Выбранный неверный GPX блокирует запуск до замены или явного удаления.
   Проверяются тип, размер и содержимое при обработке.
2. `POST /api/jobs` сохраняет файлы под внутренними именами и возвращает случайный UID.
   Повтор с тем же `X-WarpBuster-Upload-ID` в той же сессии возвращает то же задание.
   Backend принимает обязательный файл `activity` (FIT) и необязательный `course`
   (GPX). Отсутствующий GPX явно передаётся в Core как `None`; пустой или неверный
   файл остаётся ошибкой. Дубли, неизвестные поля, ручные точки и настройки coverage
   в запросе отклоняются. Для другой комбинации файлов нужен новый upload ID.
3. Браузер переходит на `/res/<uid>`. Страница показывает loader, проверяет статус
   сразу и далее через 5 секунд после завершения предыдущего запроса. При готовности
   загружает отчёт на той же странице. Ошибки сети повторяются до трёх раз, затем
   можно повторить проверку вручную. Пропавший/истёкший результат не опрашивается снова.
4. Любой, у кого есть ссылка и доступ к серверу, видит карту, блок «О забеге» и FIT diff.
   Это публичные данные по ссылке. На карте три независимых слоя: «Исходный» — исходный
   FIT, «Исправленный» — выходной FIT, «Трек» — загруженный GPX-маршрут.
5. Скачать исправленный FIT может только сессия загрузившего. Cookie проверяется
   сервером при каждом скачивании, включая HEAD и Range. UI скрывает кнопку у гостя.
   Пояснение о браузере загрузки и потере доступа при удалении cookie видно только
   владельцу рядом с кнопкой. Гости видят нейтральный результат без комментариев
   о скачивании. Интервал автоматической проверки в интерфейсе не показывается.

Публичный UID и секрет сессии — независимые случайные значения по 32 байта.
Секрет хранится в HttpOnly / SameSite=Lax cookie сроком на 30 дней; в SQLite — только
SHA-256. Он не попадает в URL, JSON или JavaScript. На HTTPS используется Secure-cookie
с префиксом `__Host-`. HTTP допускается только для локального адреса. Восстановления
доступа после удаления/истечения cookie, входа в аккаунт и переноса между браузерами нет.

Публичный JSON собирается по явному списку полей: координаты, счётчики, изменения
разрешённых FIT-полей и запрошенный блок «О забеге». В него входят средний темп,
длительность, набор/сброс высоты и километровые агрегаты, включая средний пульс,
каденс и долю дистанции с координатами. Исходные имена и пути, устройства, абсолютное
время активности, мощность и поточечная телеметрия не публикуются. Полный локальный CLI HTML-отчёт
не используется для публичной страницы. Ошибки сервера не содержат исключений Core.
API и страницы результатов имеют `no-store`, `noindex` и `no-referrer`.

Карта использует Leaflet 1.9.4 из локальных `dist/assets/vendor/leaflet/` (лицензия
сохранена рядом). Подложка загружается из OpenStreetMap; её запросы передают только
origin в Referer, без пути результата и UID. Отрисовка линий и диаграмм выполняется
в браузере. При недоступности тайлов остаются линии треков и сообщение об ошибке.
Условия подложки: https://operations.osmfoundation.org/policies/tiles/.

«О забеге» использует те же расчёты `_activity_performance`, что служебный HTML:
сводку, таблицу по километрам и две диаграммы темпа и набора/сброса высоты. Ненадёжность
дистанции определяется через тот же `distance_policy`, а не по виду линии на карте.
Если выходной FIT не создавался, явно показывается сводка исходной записи. Отсутствующие
значения остаются прочерками; километры не строятся из неполной/немонотонной дистанции.

Для ранее созданных отчётов доступно дополнение публичного JSON без перезаписи FIT:

```bash
.venv/bin/python -m warpbuster_web.refresh_results
```

Сводка берётся из сохранённого исправленного FIT, слой GPX — из пары исходников.
Если старые исходники уже удалены, GPX-слой недоступен, а качество дистанции отмечается
неопределённым. Пересчёт старого плана для оценки качества использует текущую веб-политику.
Обновление отчёта записывается в журнал с `pair_id`.

В FIT-only общий pipeline проверяет исходное GPS-покрытие по активному времени.
Порог по умолчанию — 51%; с GPX он не применяется. При отказе (`below_threshold`
или `unavailable`) OSM/DEM и writer не запускаются, job получает готовый отчёт
`unresolved` без скачивания. Решение Core сохраняется в приватном
`<uid>/private-processing-audit.json` (0600): режим и `observed_gps_coverage`.
Файл не выдаётся по HTTP. Публичная схема v5 содержит явную проекцию coverage:
статус, долю GPS, порог, активную и покрытую длительность, безопасную причину
невозможности расчёта. `unavailable` не превращается в 0%, UI использует решение
Core без повторного сравнения округлённых чисел. В `gaps` добавлены тип
`internal`/`prefix`/`suffix` и счётчики восстановленных/оставшихся точек.
Старые отчёты без новых полей отображаются с отсутствующей диагностикой coverage.

После загрузки запись истории вкладки отмечает инициатора. При gate-отказе
она заменяется на `/fix` с сообщением в `history.state`; файлы выбираются заново.
Сообщение сохраняется при reload, данные не попадают в URL. Отдельный переход
по ссылке отчёта без этой отметки не перенаправляется. Для partial-результата
возврата на форму нет; ограничения краёв показаны рядом с таблицей разрывов.
Слой GPX скрыт, если его геометрии нет.
Допустимые внутренние пропуски могут восстанавливаться по OSM/DEM, а отсутствующие
начало/конец без ручных точек остаются unresolved. Успешно записанный partial FIT
доступен для скачивания владельцу по прежним правилам.

При предоставленном GPX Core выполняет detection без GPX/OSM, затем строит базовый GPX-план. Для
eligible внутренних gaps общий pipeline вызывает coverage/ensure API OSM Manager,
готовит или повторно использует граф через OSM Routing и применяет Core GPX-first/OSM
selection. Writer вызывается один раз для итогового плана.
Веб не содержит отдельного OSM-сценария или собственных порогов: используется
`DEFAULT_REPAIR_POLICY` из Core, как в `warpbuster process activity.fit course.gpx`.
Эквивалентные параметры прежней команды `repair` для GPX:

```text
--fill-missing-from-course
--min-invalidation-confidence medium
--min-confidence medium
```

Заполнение пропусков координат по GPX включено; оба порога — MEDIUM. Прежние
defaults команды `repair` сохранены. Политика действует на новые загрузки;
существующие результаты не пересчитываются автоматически.
При любой ошибке acquisition/cache/prepare/routing базовый GPX-план сохраняется, а
публичный отчёт получает безопасный stage/error code. Если изменений нет или уверенности недостаточно,
исправленный файл не создаётся. Если применена только часть плана, это показано
в результате. Время и датчики сохраняются по действующему контракту Core.

## Хранение и ограничения

Приватные данные по умолчанию: `.warpbuster-web/` в корне репозитория, в `.gitignore`.
Директория имеет права 0700, файлы загрузок и SQLite — 0600. Она находится вне
статического каталога; HTTP-сервер раздаёт только известные страницы и `/assets`.
Не размещайте её под другим статическим сервером и не коммитьте пользовательские FIT.

Исходные файлы хранятся в `uploads/<uid>/`, под внутренними именами
`original.fit` и, при наличии GPX, `course.gpx`. Обработчик читает их оттуда,
а результат пишет в `<uid>/`.
SQLite хранит `jobs.has_course`; режим не определяется наличием файла на диске.
Миграция старой базы задаёт прежним jobs `has_course=1`. Потерянный GPX у такого
задания вызывает `invalid_gpx`, а не переключение в FIT-only. Режим сохраняется
при перезапуске, повторе запроса и refresh отчёта. Старые вызовы `process_job`
без нового аргумента `has_course` по-прежнему ожидают FIT+GPX.
Пара сохраняется после успешной обработки, ошибки или timeout. Неполные/отклонённые
загрузки удаляются; они не становятся хранимыми парами. При обновлении сервера ещё
не обработанные пары старого формата переносятся в `uploads/`. Исходники, уже удалённые
старой версией после обработки, восстановить нельзя.

Исходная пара, отчёт и исправленный FIT удаляются worker после 7 дней от загрузки. Пока сервер выключен,
очистка не выполняется; по истечении срока API всё равно отказывает в доступе, а
при следующем запуске данные очищаются. Метаданные истёкшего результата сохраняются
ещё 7 дней для ответа 410, затем удаляются.

## Превью ссылок

Сервис формирует `title`, `description`, canonical URL, Open Graph и Twitter Card
непосредственно в HTML главной и `/res/<uid>`. JavaScript и cookie для чтения превью
не нужны. Разметка следует [Open Graph](https://ogp.me/); изображение — общее трейловое
фото `/assets/social-preview.jpg` (JPEG, 1200 × 800, около 257 КиБ), без геометрии пользовательского маршрута.
Все абсолютные ссылки используют `WARPBUSTER_WEB_ORIGIN`, а не заголовки прокси.

Для готового результата берутся только публичные дистанция, время, темп, набор высоты
и исход обработки. Отсутствующие показатели пропускаются, неопределённость дистанции
и частичное восстановление отмечаются в описании. Пока идёт обработка или после ошибки
выдаётся описание состояния. Истёкший результат возвращает HTML с кодом 410, отсутствующий —
404; сохранённые показатели в их превью не включаются. Доступ к скачиванию не меняется.

Локально метаданные доступны через Python-сервис. Статический просмотр `dist/` не
подставляет домен и индивидуальные показатели. Для превью в мессенджерах нужен доступный
им сервер с публичным HTTPS-адресом в `WARPBUSTER_WEB_ORIGIN`; развёртывание остаётся
отдельным шагом. Мессенджер может сохранить полученное превью в своём кеше, в том числе
статус «обрабатывается» или показатели после истечения срока хранения у нас. Удаление
результата не отзывает уже сохранённые сторонние превью.

## Локальный журнал

`logs/events.jsonl` — JSON Lines: одна запись на событие, время в UTC. `pair_id`
совпадает с UID каталога пары и страницы `/res/<uid>`. Каталоги `uploads` и `logs`
не доступны через HTTP и исключены из Git вместе с остальными приватными данными.

```text
.warpbuster-web/
  uploads/<pair_id>/original.fit
  uploads/<pair_id>/course.gpx       # только при загрузке GPX
  <pair_id>/corrected.fit
  <pair_id>/result.json
  <pair_id>/private-processing-audit.json
  logs/events.jsonl
  jobs.sqlite3
  osm/datasets/       # immutable OSM snapshots and blobs
  osm/routing/        # exact versioned Valhalla graphs
  osm/tmp/            # incomplete bounded work only
  osm/leases/         # active shared cache leases
```

В журнале фиксируются:

- `upload_started`, `file_uploaded`, `upload_completed`: начало, каждый сохранённый
  файл (роль, внутреннее имя, размер в байтах, SHA-256), завершение приёма пары;
- `upload_reused`, `upload_failed`, `upload_migrated`: повтор запроса, ошибка приёма,
  перенос ещё не обработанных исходников из прежней структуры;
- `processing_started`: полная команда, каталог пары, лимит точек/времени и три
  параметра обработки из общей с процессором конфигурации;
- `osm_pipeline_completed`: итог и длительность OSM stage, bounded coverage
  cells/area, времена coverage/acquisition/prepare/routing, cache hit/stale,
  routing/candidate counters и итоговые GPX/OSM/unresolved gaps — без координат,
  идентификаторов snapshot/graph, geometry и native stderr;
- `processing_completed`, `processing_failed`: время выполнения, код возврата,
  безопасный код ошибки, наличие выходного FIT;
- `processing_interrupted`, `pair_expired`: прерывание при перезапуске и истечение хранения.

Журнал начинается после выделения ID пары; отклонённые запросы без созданной пары
(например, без сессии) в него не включаются. Имена, присланные пользователем, cookie,
идентификаторы владельцев и содержимое FIT/GPX не логируются. Для одной пары из корня:

```bash
rg --fixed-strings 'PAIR_ID' .warpbuster-web/logs/events.jsonl*
tail -f .warpbuster-web/logs/events.jsonl
```

Файлы журнала имеют права 0600 и ротируются при достижении 5 МиБ: текущий файл и
3 предыдущих (`.1`–`.3`). Эти лимиты задаются `WebConfig.log_max_bytes` и `log_backups`.
Журнал ротируется независимо от срока хранения пар. При ошибке записи предупреждение
выводится в локальный stderr, обработка продолжает работу. Удалённого сбора логов нет.

Команда процессора теперь явно разделяет каталоги входа и выхода:

```bash
.venv/bin/python -m warpbuster_web.processing .warpbuster-web/PAIR_ID 100000 --inputs .warpbuster-web/uploads/PAIR_ID
```

Существующий выходной FIT не перезаписывается. Обычный запуск выполняет очередь;
повторно запускать эту команду для уже готового результата не требуется.

## Лимиты и конфигурация

Лимиты задаются в `WebConfig`: 20 МиБ на файл, 41 МиБ на запрос (в том числе без
Content-Length), 60 секунд на загрузку, 600 секунд на обработку, 100 000 точек,
50 незавершённых заданий, 1000 хранимых результатов и 100 результатов на сессию.
Это лимиты локального сервиса; распределённой очереди и защиты публичного сервера
от массового создания сессий в этой задаче нет.

Переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `YANDEX_METRIKA_ID` | пусто | Публичный ID счётчика; пустое значение отключает Метрику |
| `WARPBUSTER_WEB_ORIGIN` | `http://127.0.0.1:8000` | Точный origin без завершающего `/` |
| `WARPBUSTER_WEB_DATA` | `.warpbuster-web` | Приватные SQLite и файлы |
| `WARPBUSTER_WEB_STATIC` | `web/dist` рядом с editable-пакетом | Статические ассеты |
| `WARPBUSTER_WEB_MAX_JOBS` | `1000` | Максимум неистёкших заданий суммарно |
| `WARPBUSTER_WEB_MAX_OWNER_JOBS` | `100` | Максимум неистёкших заданий одной cookie-сессии |
| `WARPBUSTER_WEB_MAX_PENDING_JOBS` | `50` | Максимум загрузок, заданий в очереди и обработке |
| `WARPBUSTER_WEB_MINIMUM_OBSERVED_GPS_COVERAGE_PERCENT` | `51.0` | Минимальная доля исходного GPS по активному времени, только FIT-only; конечное число в `(0, 100]`, validation Core |
| `WARPBUSTER_WEB_MAXIMUM_OBSERVED_GPS_INTERVAL_SECONDS` | `30.0` | Максимальный активный интервал между исходными GPS-точками для coverage; конечное положительное число, validation Core |
| `WARPBUSTER_WEB_OSM_MODE` | `auto` | `auto`, `offline` или аварийное `disabled` |
| `WARPBUSTER_WEB_APPROXIMATE_OSM` | `true` | Task 021 для полностью отсутствующих GNSS-координат; `false` отключает зависимые этапы по умолчанию |
| `WARPBUSTER_WEB_DEM_MODE` | `auto` | `disabled`, `offline` или `auto`; по умолчанию следует OSM mode |
| `WARPBUSTER_WEB_DEM_SNAPSHOT_ID` | не задан | Точный verified `sha256:` snapshot из `/data/dem`; только при DEM mode |

### Cache и отказоустойчивость

`auto` допускает bounded acquisition; `offline` использует только полное verified
покрытие, включая явно помеченный stale snapshot; `disabled` немедленно оставляет
GPX-only pipeline. Cache и graph entries публикуются атомарно companion packages,
параллельные ensure/prepare дедуплицируются их locks, а активные snapshot/graph
удерживаются shared lease. Неполные staging entries не считаются READY.

Для rollback установите `WARPBUSTER_WEB_OSM_MODE=disabled` и перезапустите сервис:
Core/GPX path продолжит работать без Valhalla и сети. При `cache_quota`, corrupt
manifest, engine mismatch или timeout не удаляйте cache вручную во время обработки;
остановите worker, сохраните приватный audit и используйте companion `doctor/list/prune`.
Readiness не проверяет доступность Overpass, потому что сетевой сбой не должен отключать
GPX-восстановление.

DEM cache хранится в `WARPBUSTER_WEB_DATA/dem` (в контейнере
обычно `/data/dem`). Режимы `OSM=auto` и `DEM=auto` по умолчанию могут передавать
внешним поставщикам необходимую географическую область трека для получения карты
и высот; исходные FIT/GPX, временные метки и датчики им не передаются.
Отсутствующий или непригодный DEM, включая offline cache miss,
не отменяет уже выбранный безопасный 2D OSM-маршрут. Для rollback достаточно снять
`WARPBUSTER_WEB_APPROXIMATE_OSM=false`; DEM и дополнение высоты тогда выключаются
автоматически, если явно не заданы противоречащие значения. Для заданий с approximate OSM публичный отчёт имеет schema v5 с
allowlisted route/DEM evidence и предупреждением о неподтверждённом маршруте;
старые отчёты остаются v3. Приватный FIT/route geometry и raw DEM samples туда не входят.
Опциональное 021E-дополнение высоты в Web допускается только при полностью отсутствующей
высотной серии исходного FIT: сервис не может объявить vertical datum частично
заполненного пользовательского файла совместимым. Отказ высотного этапа оставляет
координатное 2D-восстановление; публичный отчёт показывает только статус и счётчики,
не исходные или DEM-высоты по отдельным records.

### Admin CLI

Пакет устанавливает отдельную команду `warpbuster-admin` (также доступную как
`python -m warpbuster_web.admin`) для очистки пар по UTC-дате и полного OSM cache.
Без `--confirm DELETE` команды выполняют только dry-run. Подтверждённая очистка
требует свободного `worker.lock`, поэтому основной web worker должен быть остановлен.
Production-вызовы через одноразовый Compose container описаны в локальном
`PRODUCTION.md`; HTTP admin endpoint намеренно отсутствует.

Пример другого локального порта:

```bash
WARPBUSTER_WEB_ORIGIN=http://127.0.0.1:8001 .venv/bin/python -m warpbuster_web --port 8001
```

## Контейнер

Публичный корневой `Dockerfile` собирает Core, Web, Manager и Routing в отдельной
build-стадии и закрепляет `pyvalhalla==3.8.3`. Runtime содержит тот же engine,
который включается в graph identity. Процесс работает
от UID/GID `10001`, слушает `8080` и записывает постоянные данные только в `/data`.
Корневая файловая система совместима с read-only режимом; для multipart-файлов нужен
записываемый `/tmp`. `.dockerignore` исключает Git, окружения, тесты, кэши и любые
FIT/GPX из build context.

```bash
docker build --pull -t warpbuster:local .
docker volume create warpbuster-data
docker run --rm --read-only \
  --memory=3g --cpus=2 --pids-limit=256 \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --mount type=volume,source=warpbuster-data,target=/data \
  -e WARPBUSTER_WEB_ORIGIN=http://127.0.0.1:8080 \
  -p 127.0.0.1:8080:8080 \
  warpbuster:local
```

Volume должен иметь не менее 12 GiB свободного места при defaults: cache quota 10 GiB,
1 GiB publication reserve и место для uploads/results. Маленький временный `/data`
подходит только для GPX smoke с `WARPBUSTER_WEB_OSM_MODE=disabled`.

`GET /health` проверяет доступность SQLite и фонового worker. Ответ содержит только
`{"status":"ok"}` либо `{"status":"unavailable"}`, не создаёт cookie и не раскрывает
путь к базе или текст внутренней ошибки. В образ встроена HTTP healthcheck этого пути.

Production Compose и `.env` намеренно не находятся в публичном репозитории. На hive
они будут лежать уровнем выше публичного clone, в `/apps/focus-hive-site-warpbuster/`,
а `build.context` будет указывать на `./repo`. Постоянный bind mount —
`/apps/focus-hive-site-warpbuster/data:/data`. Его нужно заранее создать с владельцем
`10001:10001` и правами `0700`. Внешняя сеть Traefik и публикация будут настроены
отдельным этапом после выбора домена.

Worker использует `fcntl` и рассчитан на macOS/Linux. В production должен работать
ровно один контейнер и один Uvicorn worker для одного `/data`. Приватная статическая
демоверсия Sites этой задачей не обновляется.

## Проверки

```bash
.venv/bin/python -m pytest tests web/tests -q
node --test web/tests/*.test.mjs
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

Интеграционные тесты используют синтетический FIT с доказанным скачком: проверяют
настоящую запись и чтение исправленного файла, публичную проекцию, независимых
владельцев, гостя, истечение cookie и результата, очередь, неверные файлы, лимиты,
перезапуск и timeout, хранение пар, корреляцию событий, параметры вызовов и ротацию
журнала. Node-тесты проверяют выбор файлов и опрос раз в 5 секунд,
отсутствие параллельных запросов, остановку и повтор после сетевых ошибок.

`test_fit_only_backend.py` дополнительно проверяет миграцию SQLite, явный режим,
отказы coverage до optional stages, независимость последовательных jobs,
retention/доступ и совпадение FIT с CLI на синтетическом offline OSM-кеше.
Прямой вызов обработчика проверяет реальный routing на macOS/Linux; вариант через
изолированный worker выполняется только на Linux, где поддерживается OSM isolation.

Для проверки уже запущенного локального сервиса с настоящей очередью и worker:

```bash
WARPBUSTER_ACCEPTANCE_ORIGIN=http://127.0.0.1:8023 \
  .venv/bin/python -m pytest web/tests/test_live_acceptance.py -q
```

Укажите порт своего сервиса. Четыре opt-in проверки используют синтетические FIT/GPX,
отдельные HTTP-сессии и прямое соединение с loopback без системного прокси.
Они проверяют три состояния FIT-only coverage и GPX repair, включая скачивание
GET/HEAD/Range владельцем и запрет скачивания без cookie или чужой сессией.
Тесты создают новые jobs; файлы удаляются по обычным правилам retention сервиса.
Без переменной окружения эти четыре теста пропускаются. Linux regression и
browser smoke описаны в [отчёте 023C](../tasks/023-fit-only-web.md#10-результат-023c).

## SEO, счётчик и канонический домен

`/robots.txt` разрешает публичные страницы и ассеты, закрывает `/api/` и `/health`.
Страницы `/res/<uid>` доступны для обхода ради OG-превью, но исключены из поиска
через meta robots и `X-Robots-Tag: noindex, nofollow, noarchive`. Тот же заголовок
защищает JSON и скачивания. Не добавляйте `Disallow: /res/`: поисковик должен прочитать
`noindex` ([пояснение Google](https://developers.google.com/search/docs/crawling-indexing/block-indexing)).
Это управление индексированием, а не замена проверки владельца при скачивании.

Неизвестные страницы возвращают оформленный HTML с HTTP 404 и `noindex`;
неизвестные API-пути сохраняют JSON-ответы. В футере всех страниц есть Telegram автора.

Яндекс Метрика по умолчанию отключена. Для включения задайте `YANDEX_METRIKA_ID`
в окружении сервера и перезапустите приложение. Пустое значение в `.env.example`
означает отсутствие интеграции: HTML не содержит ни скрипта, ни noscript-пикселя.
При включении сервер подставляет только публичный ID в HTML; пересборка фронтенда
не нужна. Подключение выполняется через `assets/metrika.js` и noscript-пиксель.

Приложение читает переменные окружения, но не загружает `.env` самостоятельно.
В приватном Compose добавьте в `services.<service>.environment`:

```yaml
YANDEX_METRIKA_ID: ${YANDEX_METRIKA_ID:-}
```

Сам ID храните в приватном `.env` (он исключён из Git). Для локального запуска
можно передать переменную перед командой запуска сервера. ID проверяется при
старте; допускается положительное целое число, безопасное для JavaScript.
Собственные события и цели пока не отправляются.

Параметры из предоставленного кода сохранены, включая Вебвизор, карту кликов,
учёт ссылок и ecommerce. Счётчик работает и на странице результата: её URL и
публичное содержимое могут передаваться Яндексу; это отражено в FAQ.
CSP разрешает внешнюю загрузку скрипта и адреса коллекторов по
[инструкции Яндекса](https://yandex.ru/support/metrica/ru/code/install-counter-csp).
Встраивание самого сайта в сторонние iframe по-прежнему запрещено.

Приложение возвращает 301 с `www.<WARPBUSTER_WEB_ORIGIN hostname>` на настроенный
origin, сохраняя путь и query string. Для production нужны DNS-запись
`www`, маршрутизация обоих имён в сервис и действующий TLS-сертификат для обоих.
В локальном, исключённом из Git `docker-compose.prod.yml` для www настроен
отдельный Traefik router с certresolver `letsencrypt`. Он передаёт запрос
приложению, которое возвращает 301 для всех HTTP-методов. Путь и query string
сохраняются. HTTP переводится на HTTPS общей настройкой entrypoint.


Проверка после развёртывания:

```bash
curl -I https://www.warpbuster.ru/faq
curl https://warpbuster.ru/robots.txt
curl -A TelegramBot https://warpbuster.ru/
curl -I https://warpbuster.ru/assets/social-preview.jpg
```

Превью нужно дополнительно проверить отправкой ссылки в Telegram: автоматические
тесты проверяют серверный HTML и изображение, но не кеш и решения мессенджера.
