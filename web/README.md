# WarpBuster Web

Отдельный веб-пакет для задачи [013](../tasks/013-web-processing-and-result-privacy.md).
Статические страницы находятся в `dist/`, Python-сервис — в `backend/warpbuster_web/`.
Сервис вызывает существующее ядро; алгоритмы и зависимости Core не меняются.

Страница `/faq` (`dist/faq/index.html`) кратко описывает принцип сохранения данных,
восемь этапов обработки, хранение файлов, cookie и доступ по публичной ссылке.
Доступна без JavaScript с главной, страницы загрузки и результата. При изменении
сроков хранения, политики восстановления или публичных показателей обновляйте и FAQ.

## Локальный запуск

Из корня репозитория, в окружении Python 3.14:

```bash
.venv/bin/python -m pip install -e . -e 'web[dev]'
.venv/bin/python -m warpbuster_web
```

Открыть <http://127.0.0.1:8000/fix>. Используйте один и тот же адрес: cookie для
`localhost` и `127.0.0.1` различаются. Сервер слушает только loopback по умолчанию.
Статический `python -m http.server` подходит для просмотра вёрстки, но не для обработки.

Один процесс сервера обслуживает страницы, API и устойчивую очередь SQLite.
Один фоновый worker последовательно запускает отдельный Python-процесс на задание.
Файловая блокировка предотвращает запуск двух worker для одной директории данных.
Не использовать несколько Uvicorn workers. При перезапуске очередь сохраняется;
прерванные загрузки/обработки получают понятную ошибку. Неполные загрузки удаляются,
а полностью принятая пара сохраняется даже после прерванной обработки.

## Сценарий и доступ

1. `/fix` создаёт анонимную сессию, принимает ровно два файла: исходный FIT активности
   и GPX запланированного маршрута. Проверяются тип, размер и содержимое при обработке.
2. `POST /api/jobs` сохраняет файлы под внутренними именами и возвращает случайный UID.
   Повтор с тем же `X-WarpBuster-Upload-ID` в той же сессии возвращает то же задание.
3. Браузер переходит на `/res/<uid>`. Страница показывает loader, проверяет статус
   сразу и далее через 5 секунд после завершения предыдущего запроса. При готовности
   загружает отчёт на той же странице. Ошибки сети повторяются до трёх раз, затем
   можно повторить проверку вручную. Пропавший/истёкший результат не опрашивается снова.
4. Любой, у кого есть ссылка и доступ к серверу, видит карту, блок «О забеге» и FIT diff.
   Это публичные данные по ссылке. На карте три независимых слоя: «Исходный» — исходный
   FIT, «Исправленный» — выходной FIT, «Трек» — загруженный GPX-маршрут.
5. Скачать исправленный FIT может только сессия загрузившего. Cookie проверяется
   сервером при каждом скачивании, включая HEAD и Range. UI скрывает кнопку у гостя.
   Пояснение о браузере загрузки и потере доступа при удалении cookie видно только
   владельцу рядом с кнопкой. Гости видят нейтральный результат без комментариев
   о скачивании. Интервал автоматической проверки в интерфейсе не показывается.

Публичный UID и секрет сессии — независимые случайные значения по 32 байта.
Секрет хранится в HttpOnly / SameSite=Lax cookie сроком на 30 дней; в SQLite — только
SHA-256. Он не попадает в URL, JSON или JavaScript. На HTTPS используется Secure-cookie
с префиксом `__Host-`. HTTP допускается только для локального адреса. Восстановления
доступа после удаления/истечения cookie, входа в аккаунт и переноса между браузерами нет.

Публичный JSON собирается по явному списку полей: координаты, счётчики, изменения
разрешённых FIT-полей и запрошенный блок «О забеге». В него входят средний темп,
длительность, набор/сброс высоты и километровые агрегаты, включая средний пульс,
каденс и долю дистанции с координатами. Исходные имена и пути, устройства, абсолютное
время активности, мощность и поточечная телеметрия не публикуются. Полный локальный CLI HTML-отчёт
не используется для публичной страницы. Ошибки сервера не содержат исключений Core.
API и страницы результатов имеют `no-store`, `noindex` и `no-referrer`.

Карта использует Leaflet 1.9.4 из локальных `dist/assets/vendor/leaflet/` (лицензия
сохранена рядом). Подложка загружается из OpenStreetMap; её запросы передают только
origin в Referer, без пути результата и UID. Отрисовка линий и диаграмм выполняется
в браузере. При недоступности тайлов остаются линии треков и сообщение об ошибке.
Условия подложки: https://operations.osmfoundation.org/policies/tiles/.

«О забеге» использует те же расчёты `_activity_performance`, что служебный HTML:
сводку, таблицу по километрам и две диаграммы темпа и набора/сброса высоты. Ненадёжность
дистанции определяется через тот же `distance_policy`, а не по виду линии на карте.
Если выходной FIT не создавался, явно показывается сводка исходной записи. Отсутствующие
значения остаются прочерками; километры не строятся из неполной/немонотонной дистанции.

Для ранее созданных отчётов доступно дополнение публичного JSON без перезаписи FIT:

```bash
.venv/bin/python -m warpbuster_web.refresh_results
```

Сводка берётся из сохранённого исправленного FIT, слой GPX — из пары исходников.
Если старые исходники уже удалены, GPX-слой недоступен, а качество дистанции отмечается
неопределённым. Пересчёт старого плана для оценки качества использует текущую веб-политику.
Обновление отчёта записывается в журнал с `pair_id`.

Обработка выполняет detection без GPX, затем reconstruction по GPX и проверку
записанного FIT. Веб-политика соответствует параметрам CLI:

```text
--fill-missing-from-course
--min-invalidation-confidence medium
--min-confidence medium
```

Заполнение пропусков координат по GPX включено; оба порога — MEDIUM. Настройки
Core/CLI по умолчанию не меняются. Политика действует на новые загрузки;
существующие результаты не пересчитываются автоматически.
Если изменений нет или уверенности недостаточно,
исправленный файл не создаётся. Если применена только часть плана, это показано
в результате. Время и датчики сохраняются по действующему контракту Core.

## Хранение и ограничения

Приватные данные по умолчанию: `.warpbuster-web/` в корне репозитория, в `.gitignore`.
Директория имеет права 0700, файлы загрузок и SQLite — 0600. Она находится вне
статического каталога; HTTP-сервер раздаёт только известные страницы и `/assets`.
Не размещайте её под другим статическим сервером и не коммитьте пользовательские FIT.

Исходные FIT/GPX хранятся отдельными парами в `uploads/<uid>/`, под внутренними именами
`original.fit` и `course.gpx`. Обработчик читает их оттуда, а результат пишет в `<uid>/`.
Пара сохраняется после успешной обработки, ошибки или timeout. Неполные/отклонённые
загрузки удаляются; они не становятся хранимыми парами. При обновлении сервера ещё
не обработанные пары старого формата переносятся в `uploads/`. Исходники, уже удалённые
старой версией после обработки, восстановить нельзя.

Исходная пара, отчёт и исправленный FIT удаляются worker после 7 дней от загрузки. Пока сервер выключен,
очистка не выполняется; по истечении срока API всё равно отказывает в доступе, а
при следующем запуске данные очищаются. Метаданные истёкшего результата сохраняются
ещё 7 дней для ответа 410, затем удаляются.

## Превью ссылок

Сервис формирует `title`, `description`, canonical URL, Open Graph и Twitter Card
непосредственно в HTML главной и `/res/<uid>`. JavaScript и cookie для чтения превью
не нужны. Разметка следует [Open Graph](https://ogp.me/); изображение — общее трейловое
фото `/assets/trail.png` (PNG, 1536 × 1024), без геометрии пользовательского маршрута.
Все абсолютные ссылки используют `WARPBUSTER_WEB_ORIGIN`, а не заголовки прокси.

Для готового результата берутся только публичные дистанция, время, темп, набор высоты
и исход обработки. Отсутствующие показатели пропускаются, неопределённость дистанции
и частичное восстановление отмечаются в описании. Пока идёт обработка или после ошибки
выдаётся описание состояния. Истёкший результат возвращает HTML с кодом 410, отсутствующий —
404; сохранённые показатели в их превью не включаются. Доступ к скачиванию не меняется.

Локально метаданные доступны через Python-сервис. Статический просмотр `dist/` не
подставляет домен и индивидуальные показатели. Для превью в мессенджерах нужен доступный
им сервер с публичным HTTPS-адресом в `WARPBUSTER_WEB_ORIGIN`; развёртывание остаётся
отдельным шагом. Мессенджер может сохранить полученное превью в своём кеше, в том числе
статус «обрабатывается» или показатели после истечения срока хранения у нас. Удаление
результата не отзывает уже сохранённые сторонние превью.

## Локальный журнал

`logs/events.jsonl` — JSON Lines: одна запись на событие, время в UTC. `pair_id`
совпадает с UID каталога пары и страницы `/res/<uid>`. Каталоги `uploads` и `logs`
не доступны через HTTP и исключены из Git вместе с остальными приватными данными.

```text
.warpbuster-web/
  uploads/<pair_id>/original.fit
  uploads/<pair_id>/course.gpx
  <pair_id>/corrected.fit
  <pair_id>/result.json
  logs/events.jsonl
  jobs.sqlite3
```

В журнале фиксируются:

- `upload_started`, `file_uploaded`, `upload_completed`: начало, каждый сохранённый
  файл (роль, внутреннее имя, размер в байтах, SHA-256), завершение приёма пары;
- `upload_reused`, `upload_failed`, `upload_migrated`: повтор запроса, ошибка приёма,
  перенос ещё не обработанных исходников из прежней структуры;
- `processing_started`: полная команда, каталог пары, лимит точек/времени и три
  параметра обработки из общей с процессором конфигурации;
- `processing_completed`, `processing_failed`: время выполнения, код возврата,
  безопасный код ошибки, наличие выходного FIT;
- `processing_interrupted`, `pair_expired`: прерывание при перезапуске и истечение хранения.

Журнал начинается после выделения ID пары; отклонённые запросы без созданной пары
(например, без сессии) в него не включаются. Имена, присланные пользователем, cookie,
идентификаторы владельцев и содержимое FIT/GPX не логируются. Для одной пары из корня:

```bash
rg --fixed-strings 'PAIR_ID' .warpbuster-web/logs/events.jsonl*
tail -f .warpbuster-web/logs/events.jsonl
```

Файлы журнала имеют права 0600 и ротируются при достижении 5 МиБ: текущий файл и
3 предыдущих (`.1`–`.3`). Эти лимиты задаются `WebConfig.log_max_bytes` и `log_backups`.
Журнал ротируется независимо от срока хранения пар. При ошибке записи предупреждение
выводится в локальный stderr, обработка продолжает работу. Удалённого сбора логов нет.

Команда процессора теперь явно разделяет каталоги входа и выхода:

```bash
.venv/bin/python -m warpbuster_web.processing .warpbuster-web/PAIR_ID 100000 --inputs .warpbuster-web/uploads/PAIR_ID
```

Существующий выходной FIT не перезаписывается. Обычный запуск выполняет очередь;
повторно запускать эту команду для уже готового результата не требуется.

## Лимиты и конфигурация

Лимиты задаются в `WebConfig`: 20 МиБ на файл, 41 МиБ на запрос (в том числе без
Content-Length), 60 секунд на загрузку, 180 секунд на обработку, 100 000 точек,
50 незавершённых заданий, 1000 хранимых результатов и 100 результатов на сессию.
Это лимиты локального сервиса; распределённой очереди и защиты публичного сервера
от массового создания сессий в этой задаче нет.

Переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `WARPBUSTER_WEB_ORIGIN` | `http://127.0.0.1:8000` | Точный origin без завершающего `/` |
| `WARPBUSTER_WEB_DATA` | `.warpbuster-web` | Приватные SQLite и файлы |
| `WARPBUSTER_WEB_STATIC` | `web/dist` рядом с editable-пакетом | Статические ассеты |
| `WARPBUSTER_WEB_MAX_JOBS` | `1000` | Максимум неистёкших заданий суммарно |
| `WARPBUSTER_WEB_MAX_OWNER_JOBS` | `100` | Максимум неистёкших заданий одной cookie-сессии |
| `WARPBUSTER_WEB_MAX_PENDING_JOBS` | `50` | Максимум загрузок, заданий в очереди и обработке |
| `WARPBUSTER_WEB_PORT` | `8080` | Порт только для встроенной контейнерной healthcheck |

Три переменные лимитов принимают только целые положительные числа. Некорректное
значение останавливает запуск сервиса с указанием имени переменной.

Пример другого локального порта:

```bash
WARPBUSTER_WEB_ORIGIN=http://127.0.0.1:8001 .venv/bin/python -m warpbuster_web --port 8001
```

## Контейнер

Публичный корневой `Dockerfile` собирает Core и web-пакет в отдельной build-стадии,
а в runtime оставляет только wheels, Python 3.14 и статические файлы. Процесс работает
от UID/GID `10001`, слушает `8080` и записывает постоянные данные только в `/data`.
Корневая файловая система совместима с read-only режимом; для multipart-файлов нужен
записываемый `/tmp`. `.dockerignore` исключает Git, окружения, тесты, кэши и любые
FIT/GPX из build context.

```bash
docker build --pull -t warpbuster:local .
docker run --rm --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --tmpfs /data:rw,noexec,nosuid,size=128m,uid=10001,gid=10001,mode=0700 \
  -e WARPBUSTER_WEB_ORIGIN=http://127.0.0.1:8080 \
  -p 127.0.0.1:8080:8080 \
  warpbuster:local
```

`GET /health` проверяет доступность SQLite и фонового worker. Ответ содержит только
`{"status":"ok"}` либо `{"status":"unavailable"}`, не создаёт cookie и не раскрывает
путь к базе или текст внутренней ошибки. В образ встроена HTTP healthcheck этого пути.

Production Compose и `.env` намеренно не находятся в публичном репозитории. На hive
они будут лежать уровнем выше публичного clone, в `/apps/focus-hive-site-warpbuster/`,
а `build.context` будет указывать на `./repo`. Постоянный bind mount —
`/apps/focus-hive-site-warpbuster/data:/data`. Его нужно заранее создать с владельцем
`10001:10001` и правами `0700`. Внешняя сеть Traefik и публикация будут настроены
отдельным этапом после выбора домена.

Worker использует `fcntl` и рассчитан на macOS/Linux. В production должен работать
ровно один контейнер и один Uvicorn worker для одного `/data`. Приватная статическая
демоверсия Sites этой задачей не обновляется.

## Проверки

```bash
.venv/bin/python -m pytest tests web/tests -q
node --test web/tests/*.test.mjs
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

Интеграционные тесты используют синтетический FIT с доказанным скачком: проверяют
настоящую запись и чтение исправленного файла, публичную проекцию, независимых
владельцев, гостя, истечение cookie и результата, очередь, неверные файлы, лимиты,
перезапуск и timeout, хранение пар, корреляцию событий, параметры вызовов и ротацию
журнала. Node-тесты проверяют выбор файлов и опрос раз в 5 секунд,
отсутствие параллельных запросов, остановку и повтор после сетевых ошибок.
