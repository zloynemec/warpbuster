# Task 012D — Выбор лучшего кандидата для разрыва

Статус: реализовано и проверено локально 2026-09-14.
Продуктовое продолжение уточнено: [012E](012e-automatic-osm-application.md) —
GPX-first и автоматический OSM fallback. Ручного выбора в первой версии нет;
общий ranking этого этапа остаётся advisory и не отменяет приоритет принятого GPX.
Зависимости: 010I (приближённый OSM discovery), 012A (bridge), 012B (application API).
Выполнить до подключения выбора кандидатов к web в 012C.

## 1. Цель

Для каждого внутреннего разрыва сравнить доступные GPX- и OSM-кандидаты по единым
правилам, предложить предпочтительный путь и объяснить решение человеку.
Восстанавливается примерный путь по лесу: различия в несколько метров не должны
определять победителя или блокировать рекомендацию. Допуск привязки до 100 м из
010I сохраняется. Отличать слабую поддержку пути от физически невозможного маршрута.

Сейчас OSM primary — первый прошедший аудит маршрут из первой пары привязок.
GPX и OSM собираются совместно, но общего сравнения нет. MEDIUM/LOW discovery и
стоимость Valhalla не являются общей шкалой качества GPX/OSM.

## 2. Результат и границы

Добавить детерминированный Core ranking после завершения discovery обоих источников.
Он возвращает рекомендацию и оценки, но не изменяет существующий repair plan.
Это сознательно ограниченный этап: recommendation можно проверить до подключения
к записи FIT. В HTML отдельно показывать рекомендованный путь и текущий GPX preview.

Входит:

- единое представление доступных кандидатов и вариантов привязки;
- предварительная проверка сравнимости и физической допустимости;
- общий score с грубыми диапазонами и явными причинами;
- recommendation, близкие варианты, неопределённость и полнота поиска;
- JSON/HTML/console, синтетические тесты и повторный private прогон пяти треков.

Не входит: новый поиск GPX/OSM, расширение graph coverage, изменение detector, mask,
границ разрыва, timestamps, сенсорных полей или правдоподобных координат; автоматическая
запись рекомендации в FIT; генерация confirmation; изменение GPX-first application
012B; CLI/UI подтверждения; DEM; web worker, Docker, deployment.
Рекомендация OSM может отличаться от GPX preview — это явно объясняется в отчёте.

## 3. Контракт

Типы: `GapCandidateRankingConfig`, `GapCandidateRanking`,
`RankedGapCandidate`, `CandidateRankingEvidence`.

Вход: immutable activity/IntegrityResult/gap inventory, исходные GPX планы,
OSM discovery и конфигурация. Routing не импортирует Core и не принимает GPX.

Сравнивать только candidates с одним gap ID, одинаковым write scope и одинаковыми
исходными anchors. GPX extraction берёт только геометрию соответствующего участка
в порядке обхода, не весь course. Несовпадение scope/anchors даёт `incomparable`,
а не искусственное подрезание пути. Prefix/suffix — `not_supported` в этом этапе.

Для OSM сохраняется route ID; для GPX вводится стабильный ID из геометрии, направления,
course identity и scope. Не использовать позицию в массиве как идентичность.
Для разных attachment_options одного OSM route оценивать каждый вариант целиком,
выбирать лучший допустимый; нельзя смешивать начало одного и конец другого.

Выход на gap:

- `status`: `recommended`, `ambiguous`, `insufficient_evidence`, `no_eligible_candidates`,
  `not_supported`, `resource_limit`;
- `recommended_candidate_id`: только при `recommended`;
- `candidates`: ID/provider, eligibility, score, компоненты, значения/единицы,
  missing evidence, reasons, выбранный attachment и исходный discovery role;
- `best_score`, `score_margin`, `near_best_candidate_ids`, `search_complete`;
- версия policy, конфигурация, provenance исходных candidates;
- `application_allowed=false` для результата ranking.

`search_complete=false`, если хотя бы один provider сообщает truncation/ошибку/лимит.
Не считать отсутствие alternatives доказательством уникальности. Можно рекомендовать
лучший из найденных при неполном поиске, обязательно с этим пояснением.

## 4. Eligibility до score

Отказ кандидату разрешён только по явным причинам:

1. Невалидная геометрия, несовпадение scope/anchors или непройденный обязательный
   routing audit. Нормальный WARN приблизительной привязки не является отказом.
2. Connector > 100 м. Для GPX применяется тот же предел, без ослабления его discovery.
3. Непригодная хронология, открытая/неразрешённая пауза или отсутствие активного времени.
4. Полная длина пути с connectors / активное время превышает существующий физический
   лимит Core для новых transitions. Это необходимая проверка, а не гарантия, что
   дальнейшая allocation пройдёт все проверки записи.

Переиспользовать Core clock/signal qualification. Не создавать вторые алгоритмы
семантики FIT distance/speed. Ненадёжный или отсутствующий сигнал — missing evidence,
без отказа. Расхождение надёжной дистанции — штраф ranking; существующие более строгие
application gates 012B остаются самостоятельными и могут позже отказать в записи.

## 5. Оценка кандидатов

Меньший score предпочтительнее. Начальные defaults — общие для всех треков;
не калибровать их под получение конкретного победителя Andromeda.
Все новые числа — именованные поля конфигурации с единицами, диапазоном и тестом.

| Компонент | Определение | Штраф |
| --- | --- | --- |
| Привязки | Максимум расстояний начала/конца | ≤25 м: 0; ≤50 м: 1; ≤100 м: 2 |
| Контекст подхода | Медианное расстояние допустимых исходных точек до пути | ≤25 м: 0; ≤50 м: 1; >50 м: 2; нет данных: 1 |
| Направление подхода | Угол между движением перед разрывом и началом пути | ≤60°: 0; ≤120°: 1; >120°: 2; нет данных: 1 |
| Дистанция | Расхождение полной длины с qualified FIT distance либо интегралом qualified speed | В допуске: 0; до двойного допуска: 1; выше: 2; нет данных: 1 |

`score = 2 × привязки + контекст + направление + 2 × дистанция`.
Весы 2/1/1/2 также находятся в config. Целочисленные диапазоны намеренно не различают
сантиметры и небольшие GPS колебания. Округление для отображения не влияет на score.

Дистанционный допуск: `max(100 м, 20% от qualified reference distance)`.
В полную длину входят оба connectors, рассчитанные одинаковым Core методом для GPX/OSM.
Не использовать native Valhalla cost/time как FIT distance или вероятность пути.
Если qualified distance и speed оба доступны, рассчитать обе проверки и взять худший
штраф один раз; не суммировать зависимые свидетельства. Сохранить обе в evidence.
Не использовать координатную длину внутри damaged gap как независимый сигнал.

Контекст: тот же допустимый непрерывный suffix до разрыва, что собирает 010H/010I,
без переноса через G1, остановки или неeligible records. Геометрическое сравнение
единое для providers: расстояния до участка пути, примыкающего к началу, длиной
до 150 м, а также его начального connector. Минимум 8 исходных точек; иначе missing.
GPX и OSM не получают бонус за совпадение друг с другом: course assumption не
является независимым свидетельством фактически пройденного пути.

Направление: исходный вектор от первой к последней точке пригодного suffix;
если его длина <20 м, признак missing. Вектор пути от начала геометрии до позиции
через 30 м по chainage; если весь путь короче 20 м, признак missing. Connector не
определяет направление пути. Эти defaults также входят в config. Отдельные шумные
точки или несовпадение направления создают штраф, но не veto.

## 6. Решение и близкие варианты

После eligibility сортировать по score, при равенстве — по стабильному candidate ID.
ID обеспечивает воспроизводимость отображения и никогда не разрешает неоднозначность.
Provider, прежний primary, discovery confidence и порядок входа не дают бонусов.

Начальные defaults:

- `maximum_recommended_score = 5`;
- `minimum_score_margin = 2`;
- `minimum_observed_evidence_components = 2` из четырёх компонентов выше;
- `near_best_score_delta = 1`.

Правила:

1. Нет допустимых кандидатов → `no_eligible_candidates`.
2. Лучший score >5 или у лидера меньше двух наблюдаемых компонентов →
   `insufficient_evidence`; рекомендация отсутствует.
3. Есть runner-up и разница score <2 → `ambiguous`; показать близкие варианты.
4. Иначе → `recommended`, включая случай единственного пригодного кандидата,
   если соблюдены качество и достаточность evidence. Написать «лучший из найденных»,
   а для единственного — «единственный найденный пригодный вариант».

Не вводить новый HIGH или вероятность правильности пути. Recommendation не повышает
discovery/application confidence и не является OSMRouteConfirmation.
Почти совпадающие GPX/OSM пути могут остаться ambiguous; общего геометрического
кластеризатора в этом этапе нет. Показывать оба источника без ложного преимущества.

## 7. Отчёт

В JSON добавить отдельный `candidate_ranking` без переопределения existing selection.
OSM `primary` сохранить как legacy routing provenance; в пользовательском тексте
называть «первый найденный OSM», чтобы не путать с рекомендацией.

На каждый gap показать:

- рекомендуемый provider и длину с connectors либо понятную причину отсутствия выбора;
- таблицу scores и отдельных компонентов с исходными метриками;
- разницу с ближайшим конкурентом и 2–3 решающих объяснения;
- недостающие сигналы и ограниченность поиска;
- слой рекомендованного пути и отдельное обозначение текущего repair preview;
- явное «рекомендация не применена», когда выбран OSM без application.

Пример объяснения: «Этот вариант лучше подходит к конечной точке: 5 м против 79 м.
Дистанция в FIT не прошла проверку качества и в сравнении не использовалась».
Не выводить такой текст без соответствующего evidence.

## 8. Производительность и воспроизводимость

Никаких новых network/routing запросов. Общая qualification сигналов и контекста
рассчитывается один раз на gap. Кэшировать одинаковую геометрию в пределах вызова.
Именованные limits: 64 candidates на gap, 100000 входных candidate points на activity,
60 context points, 2000000 point–segment projections на activity. При превышении
не публиковать рекомендацию из произвольно урезанного набора; `resource_limit`.
Не выполнять полный activity × polyline поиск. Для context ограничить геометрию
первыми 150 м chainage. Тестировать границы каждого бюджета.

## 9. Acceptance criteria

- Перестановка входа и прежних primary/alternative не меняет scores, решение и IDs.
- OSM может обойти GPX; GPX может обойти OSM; провайдер не даёт приоритета.
- Короткий путь с плохими привязками может проиграть более длинному; native cost
  не влияет на общий score. Connectors включены в длину обеих сторон сравнения.
- Изменения координат на сантиметры внутри диапазонов не меняют решение.
- Все пороги, веса, углы, missing rules и margins имеют boundary tests.
- Нет distance, speed или контекста: нет ложного zero penalty/автоматического veto.
  Конфликт двух qualified сигналов виден и не маскируется выбором удобного.
- Равные/близкие варианты дают ambiguous. Единственный слабый вариант не становится
  recommended из-за отсутствия альтернатив. Неполный поиск явно отражён.
- Проверены scope mismatch, malformed geometry, >100 м connector, unusable clock,
  превышение физического лимита, разные attachment_options и budget exhaustion.
- Core plans, detector masks, existing selection, исходные timestamps/координаты
  и результат FIT writer идентичны с ranking и без него. Confirmation не создаётся.
- JSON/HTML согласованы; по отображаемым компонентам можно воспроизвести score.
- Private acceptance: Andromeda, Balaklava, CHR KayaBayu, m87, BST TezBair; для G1/G2
  Andromeda сохранить сравнение всех доступных GPX/OSM и объяснение результата.
  Не требовать победы нынешнего primary 2563 м или обязательного recommended для G2.
- Приватные исходники/результаты не коммитить; проверить hashes до/после.
- Все Core/routing/manager tests, Ruff, mypy проходят; browser smoke без JS errors.
  Зафиксировать время ranking отдельно от native routing на пяти треках и synthetic
  20000 records. Завершить task только с фактическим отчётом acceptance.

## 11. Отчёт реализации

Реализован отдельный immutable ranking API. Он извлекает GPX-кандидат из
`GapRepairPlan`, принимает все аудированные OSM candidates, рассчитывает connectors,
полную длину, контекст, направление и согласованность с qualified distance/speed.
Результат добавляется в JSON/console/HTML как `candidate_ranking`; прежний selection
и writer не изменены. На карте есть отдельный слой рекомендованного пути.

Добавлено 14 синтетических test cases: recommendation, GPX/OSM ambiguity, отсутствие
provider priority, независимость от input order/role, лимит connector 100 м, устойчивость
внутри грубого диапазона, scope/audit refusal, resource limits, config validation,
additive report, воспроизводимость и 20 000 records. Полный Core: 585 passed,
17 private skipped. Routing: 450 passed.
OSM Manager: 56 passed. Ruff, Core/routing/manager mypy и `git diff --check` проходят.

Пять приватных прогонов успешны, hashes исходных FIT/GPX не изменились, FIT output
не создавался. Артефакты находятся в игнорируемой директории
`tests/private/osm-dry-run-20260914/ranking-final`.

Andromeda G2: 13 сравниваемых путей — один GPX и 12 OSM. Результат `ambiguous`:
GPX и первый OSM получили score 1 и margin 0. У обоих хорошие привязки и согласование
с qualified distance; контекст попал в лучший диапазон, направление не дало
достаточного различия. Поиск OSM помечен limited, рекомендация и FIT application
отсутствуют. Это соответствует acceptance: текущий OSM primary не получает бонуса.

Измерение ranking отдельно от routing, медиана десяти запусков: Andromeda 19 807
records / 30 входных candidates — 0.025 с; Balaklava — 0.008 с; CHR — 0.013 с;
m87 — менее 0.001 с; BST 35 853 records / 23 candidates — 0.055 с. Synthetic
20 000-record test остаётся ниже лимита 5 с.

Автоматическое применение и web production выполняются в следующих этапах;
confirmation UX исключён из первой версии по решению пользователя. DEM и геометрическая кластеризация совпадающих
GPX/OSM путей не реализованы. Ranking ограничен internal gaps с двумя anchors.
