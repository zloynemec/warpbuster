# Task 022 — FIT-only Pipeline and CLI with Optional Start/Finish

Статус: 022A реализована 2026-09-17; 022B–022D не начаты. Задача 022 в целом
не принята; CLI и разбор внутренних отчётов относятся к последующим этапам.
Предпосылки: Tasks 012C, 014, 020 и 021.

Область задачи: Core/pipeline, CLI и внутренние отчёты. Сначала реализовать,
протестировать и принять новый метод здесь, изучая внутренние JSON/HTML отчёты.
Web-интеграция вынесена в [Task 023](023-fit-only-web.md), которая начинается
только после завершения и приёмки 022. Реализация 022 не требует обновления Web.

## 1. Цель и согласованные решения

Восстанавливать забег без предоставленного пользователем GPX course. Единственный
обязательный файл — FIT; существующие OSM/DEM acquisition, cache, routing и elevation
comparison используются на тех же условиях, что в полном pipeline.

Согласовано с пользователем:

- FIT обязательно содержит сохранившиеся участки маршрута.
- `minimum_observed_gps_coverage_percent`, default **51%**, задаёт минимальную долю
  пригодного исходного GPS **по активному времени после детекции**.
- Этот порог применяется **только без GPX**. При наличии GPX он не ограничивает ни
  GPX-реконструкцию, ни OSM fallback и не меняет прежнее поведение.
- Начало достраивается только при указанном старте, конец — только при указанном
  финише. Разрешено указать только одну из этих точек.
- Пользовательская точка не имеет собственного времени. Старт условно соответствует
  началу записанной активности, финиш — её окончанию; timestamps FIT неизменяемы.
- Для одного кольца можно явно указать одну общую точку старта/финиша. Несколько
  кругов не рассматриваются.
- Сохраняется политика Task 021: для отсутствующих координат автоматически выбирается
  лучший допустимый примерный маршрут; историческая точность не гарантируется.

51% — условие достаточности исходных наблюдений, а не оценка точности результата.
Прохождение глобального порога не отменяет локальные проверки каждого разрыва.

## 2. Существующая основа и необходимые изменения

Core уже содержит course-independent detector, immutable coordinate mask, gap
inventory, OSM routing между двумя сохранёнными anchors, allocation с учётом пауз,
DEM comparison, автоматический selection, atomic FIT writer, validation и diff.

Ограничения текущей реализации:

- `run_repair` принимает `course_path=None`, но стандартная политика требует
  `fill_missing_from_course`; это ещё не законченный FIT-only workflow.
- CLI `process` требует второй файл, Web upload/worker ожидают FIT и GPX.
- `osm_gap_anchors` принимает только internal gaps с двумя сохранёнными FIT anchors.
- Task 021 допускает approximate fallback только для `ORIGINAL_MISSING` с двумя
  сохранёнными anchors; пользовательские endpoints требуют отдельного контракта.

Переиспользовать эти подсистемы. Не создавать отдельный detector или FIT writer
для нового режима; не выдавать пользовательскую точку за исходную запись FIT.

## 3. Режим обработки

Режим выбирается по наличию GPX во входном запросе:

- `fit_with_course`: прежний pipeline и GPX-first; coverage gate имеет статус
  `not_applicable`, независимо от значения FIT-only порога.
- `fit_only`: detector → mask/gaps → coverage gate → OSM/DEM reconstruction →
  allocation/selection → один atomic FIT write и отчёт.

Невалидный, пустой или непрочитанный предоставленный GPX остаётся ошибкой GPX.
Нельзя автоматически считать такой запрос FIT-only. Клиенты передают отсутствие
course явно, без пустого фиктивного файла.

В FIT-only отключается только course-specific completion; это не должно отключить
OSM completion исходных missing gaps. Старые CLI команды с GPX совместимы.
Новые пользовательские endpoints в рамках 022 принимаются только без GPX; их
совместное использование с course отклоняется понятной ошибкой параметров.

### 3.1. Обратная совместимость pipeline

Существующий формат вызова `run_repair(activity_path, course_path, output_path,
policy=..., config=..., dry_run=..., overwrite=...)` остаётся совместимым:
сохраняются порядок позиционных аргументов, существующие keyword arguments и их
смысл. Новые параметры endpoints/coverage необязательны; новые аргументы функции
добавляются как keyword-only с совместимыми defaults.

Для прежнего FIT+GPX вызова сохраняются GPX-first, политика reconstruction,
OSM/DEM defaults, существующие поля результата и семантика ошибок. Новые поля audit
аддитивны; потребителю не требуется передавать mode, endpoints или FIT-only config.
Coverage gate не влияет на обработку с GPX. Не изменять общие defaults или shared
policy objects ради включения FIT-only: режим разрешается локально для вызова.

Текущие Web adapter/worker продолжают вызывать pipeline с двумя файлами без правок
кода, конфигурации, job metadata или публичной схемы. Их существующие тесты должны
проходить с обновлённым Core. Нельзя устранять нарушение совместимости изменением
Web в 022; новый Web workflow реализуется только в 023.

## 4. Coverage gate

### 4.1. Определение

Расчёт выполняется один раз на исходной активности после построения detector mask,
до reconstruction, OSM/DEM acquisition и любых coordinate updates.

Временное окно — от первого до последнего activity record. Использовать существующие
правила timer events и объединения пауз; не заменять timeline значением session
`total_timer_time`. При отсутствии timer events действует текущая модель без явных
пауз, с отражением этого допущения в audit.

Для каждой пары соседних records вычислить `active_delta_i`: положительную разницу
timestamps за вычетом пересечения с паузами. Знаменатель `T_active` — сумма этих
дельт, включая время missing/invalidated runs и переходы через разрывы continuity.
Такие разрывы не должны искусственно уменьшать знаменатель.

Дельта входит в числитель `T_observed` только когда:

1. Оба конца имеют исходные валидные координаты, состояние `PRESERVED` и пригодны
   как anchors по исходной mask; доказанно повреждённые и неопределённые опоры
   не засчитываются.
2. Это соседние исходные records одной continuity component; переход классифицирован
   detector-ом как `NORMAL`.
3. Интервал не является длинным разрывом наблюдений по правилу §4.2.

`observed_gps_coverage_percent = 100 * T_observed / T_active`.

Дельты на входе/выходе missing run не засчитываются частично. Нельзя соединить две
хорошие точки через missing records и засчитать весь промежуток. Пользовательские
endpoints, OSM, DEM и восстановленные координаты не входят в числитель.
Метрика характеризует покрытие пригодными наблюдениями, не доказывает абсолютную
географическую истинность всех сохранённых координат.

### 4.2. Конфигурация и пограничные случаи

| Параметр | Default | Единицы / назначение |
| --- | --- | --- |
| `minimum_observed_gps_coverage_percent` | 51.0 | Проценты активного времени; конечное число в `(0, 100]`; только FIT-only |
| `maximum_observed_gps_interval_seconds` | 30.0 | Секунды активного времени между соседними наблюдениями; конечное положительное число; только расчёт FIT-only coverage |

Второй параметр — проектное решение этого ТЗ для редкой записи: две координаты через
час не означают час наблюдаемого GPS. Начальный default 30 секунд требует проверки
на синтетической неравномерной записи и выбранных private FIT при реализации.
Его изменение не влияет на detector, corruption scope или право изменения координат.
Интервал длиннее лимита целиком исключается из числителя и остаётся в знаменателе.
Длинная явная пауза не снижает покрытие сама по себе: сравнивается активная дельта.

Сравнение с порогом производится до округления для UI; ровно 51% проходит.
В 022 порог конфигурируется в Core и CLI с одинаковым default. Серверная
конфигурация Web добавляется в 023 на основе принятого Core contract.

При отсутствующих, повторяющихся или немонотонных record timestamps, неоднозначном
timer state либо `T_active <= 0` gate возвращает `unavailable` с причиной. Не
подменять метрику процентом records, нулём или предположительным временем. Корректная
финальная остановка таймера после последней записи не считается неоднозначностью.

Результат gate: `passed`, `below_threshold`, `unavailable`, `not_applicable`.
При `below_threshold`/`unavailable` FIT-only reconstruction не запускается, включая
endpoint completion и dependent altitude completion. Анализ и отчёт доступны;
исправленный FIT не создаётся. Нет скрытого обхода порога через другую точку входа
или повторный расчёт после частичного восстановления.

## 5. Пользовательские старт и финиш

### 5.1. Ввод и смысл

Входной typed contract содержит optional `start` и `finish` в WGS84 latitude/longitude
либо одну `loop_point`, явно означающую общий старт и финиш одного кольца.
`loop_point` несовместима с отдельными `start`/`finish`; координаты должны быть
конечными и находиться в допустимых диапазонах. Близость концов не включает кольцо
автоматически. GPX из пользовательских точек не генерируется.

Пользователь задаёт предполагаемое место. Запись в provenance:
`source=user_supplied`, `time_binding=activity_boundary_assumption`.
Его timestamp не считается измерением и не вставляется в FIT как новая запись.

Точка старта привязывается к timestamp первого activity record; финиш — последнего.
Все промежуточные координаты распределяются только по существующим records.
Начало записи до реального старта может дать неточное распределение движения;
это явно отмечается как допущение. Новое время, записи и timer events не создаются.

### 5.2. Разрешённый scope

- Prefix: от указанного старта до ближайшего пригодного сохранённого участка.
- Suffix: от последнего пригодного сохранённого участка до указанного финиша.
- Internal gaps: прежние две сохранённые опоры; пользовательские endpoints для них
  не заменяют отсутствующие локальные anchors.
- Для кольца prefix и suffix восстанавливаются независимо вокруг сохранившейся
  середины; нельзя строить весь круг кратчайшим маршрутом из точки в неё же.

Endpoint completion требует пригодного стабильного FIT-контекста на сохранённой
стороне. Использовать существующие проверки устойчивости и направления, а не
единственную случайную координату. Нельзя пересекать continuity boundary или
поглощать `PRESERVED`/неопределённые positioned components ради удобного маршрута.

Если координаты края уже сохранены, пользовательская точка ничего не перемещает:
отмечается как неиспользованная. Её несовпадение с FIT не является доказательством
corruption. При отсутствии точки соответствующий край остаётся unresolved; даже
для почти замкнутого маршрута нельзя неявно копировать противоположный endpoint.

## 6. Поиск, выбор и безопасность

OSM coverage включает пользовательскую точку, пригодный FIT anchor и контекст
присоединения. Сохранить существующие ограниченные budgets площади, запросов,
кандидатов, памяти и времени. Далёкий ошибочный endpoint не вызывает неограниченный
поиск. Не использовать invalidated GPS для определения территории загрузки.

Ввести явную типизацию опоры: сохранённая FIT-запись либо пользовательский endpoint.
Существующий internal-gap контракт не ослабляется глобально. Snapping и соединение
точки с OSM проходят существующий аудит attachments; исходная и snapped позиции,
connector distance и причины отказов сохраняются. Сдвиг до дороги не скрывается.
Начальная/конечная координата следует пользовательской точке с точностью FIT
quantization, а не молча заменяется snapped позицией; connector проверяется как
часть пути. Нулевой маршрут не заменяет неизвестное движение произвольной константой.

Политика по происхождению разрыва:

- `ORIGINAL_MISSING`: расширить approximate policy 021 на endpoint gaps с одной
  сохранённой опорой и одним явным пользовательским endpoint. Soft-ничья не блокирует
  физически допустимый и прошедший preflight вариант. Confidence не выше `MEDIUM`.
- `INVALIDATED`/`MIXED`: пользовательская точка разрешает endpoint candidate search,
  но не ослабляет proof, scope и консервативный selection. Нельзя переименовать
  invalidated координаты в original missing ради approximate fallback. Если
  существующие требования к выбору не выполнены, край остаётся unresolved.

DEM сравнивает доступный исходный высотный профиль с кандидатами по правилам 021.
Отсутствие/неинформативность DEM даёт 2D fallback; DEM не придумывает наблюдения и не
классифицирует GNSS. Distance/speed не считаются независимыми от GNSS без оснований.
Сохраняется allocation по пригодным signals, иначе по активному времени.

Каждый кандидат проверяется на pauses, доступное активное время, физические
переходы, coverage, attachments и FIT quantization. Если путь не помещается во время,
отказывает этот gap. Не растягивать timestamps и не менять сохранённые GPS-точки.
Отказ одного края не отменяет допустимые внутренние разрывы и другой край.

После выбора — composed preflight и один atomic writer pass. Сохраняются timestamps,
sensors, неизвестные/developer fields и существующая политика зависимых полей.
Дополнение высоты — только по текущим отдельным правилам 021. Обязательны validation
и FIT diff без unexpected changes. Core детерминирован и работает offline с готовыми
snapshots; сетевое получение OSM/DEM остаётся во внешней orchestration.

## 7. CLI и внутренние отчёты

CLI `process` получает optional course, параметры пользовательских точек и настройку
порога. Расчёт coverage, выбор режима и reconstruction выполняются в общем pipeline,
а не повторяются в CLI. Библиотечные offline defaults сохраняются; CLI использует
текущие OSM/DEM defaults. Форма Web, worker и public schema в 022 не меняются.

Внутренние JSON/HTML отчёты, используемые для приёмки нового метода, показывают:

- режим обработки, результат gate, порог и измеренную долю до reconstruction;
- `active_duration_seconds`, `observed_gps_duration_seconds`, правило редкой записи
  и причины невозможности расчёта; с GPX — `not_applicable`;
- пользовательские точки, фактическое использование и допущение привязки ко времени;
- статус каждого internal/prefix/suffix gap, причины отказа и источник anchors;
- approximate selection, исходные/восстановленные участки, OSM/DEM provenance,
  allocation method, FIT validation/diff и partial результат.

Не сообщать о полном восстановлении при unresolved gaps. При отказе по coverage
показать фактическое значение и требуемый порог; `unavailable` не отображать как 0%.
Не смешивать процент исходного покрытия с долей восстановленных координат.
Endpoint coordinates имеют ту же приватность, что FIT geometry: не публикуются
в operational logs; внутренние отчёты с private данными хранятся в ignored
директории. Публичная Web-проекция этих данных относится к 023.

## 8. Этапы реализации и предполагаемые файлы

1. **022A — Core mode/coverage:** typed mode/config/audit, единый gate и FIT-only
   internal OSM/DEM pipeline, unit/regression tests.
2. **022B — Endpoints:** typed user anchors, prefix/suffix routing, allocation,
   provenance, composed writer checks и integration tests.
3. **022C — CLI/internal reports:** optional course, параметры точек, настройка
   порога, внутренние JSON/HTML отчёты, ошибки и CLI end-to-end tests.
4. **022D — Pipeline/CLI acceptance:** synthetic/private regressions, compatibility
   с GPX и неизменённым Web, offline repeatability, performance evidence и разбор
   внутренних отчётов. Завершение этого этапа — обязательное условие начала 023.

Результат 022A: `run_repair` без GPX использует отдельную FIT-only проверку покрытия
по исходной mask и активному времени. При прохождении порога внутренние gaps идут в
существующий OSM/DEM pipeline; при отказе нет OSM/DEM stage и записи FIT.
Обновлённый тестовый сценарий с локальным OSM cache записывает валидный FIT с
восстановленным внутренним разрывом. С GPX coverage имеет `not_applicable` и
прежний вызов сохраняется. Проверки: Core 757 passed, 6 skipped; Web 111 passed;
Ruff и mypy изменённых модулей проходят. В Web тестовом файле обновлено устаревшее
ожидание событий DEM/altitude, уже присутствовавших в worker до 022A; Web-код не
менялся. Параметр 30 секунд проверен синтетическим тестом; отдельная проверка на
private FIT остаётся в 022D.

Ожидаемые области изменений при реализации (не список уже изменённых файлов):

- `src/warpbuster/pipeline/{config,repair,osm,dem}.py` и IPC worker contract;
- `src/warpbuster/models/reconstruction.py`, `reconstruction/{gaps,timing,osm,
  osm_application,automatic_osm,approximate_contract,dem_choice}.py`;
- отдельный небольшой модуль расчёта GPS coverage и endpoint contracts;
- `src/warpbuster/cli.py`, `src/warpbuster/report/`;
- `tests/`, затронутые companion tests; существующие `web/tests/` запускаются
  для проверки совместимости без реализации новых Web-сценариев;
- `docs/CLI_SPEC.md`, `docs/PRODUCT_SPEC.md` и README.

Не переписывать detector/writer/routing engine. Менять их интерфейсы только при
необходимости нового typed endpoint contract; новые thresholds документировать
с единицами, default, validation и тестами.

## 9. Проверки и acceptance criteria

Обязательные автоматические сценарии:

1. FIT-only: 50.99% не проходит, 51% и 51.01% проходят; округление UI не влияет.
2. Тот же FIT с пригодным GPX обрабатывается по прежним правилам даже при 0% или
   меньшем порога GPS; FIT-only threshold не блокирует и его OSM fallback.
3. Невалидный предоставленный GPX не переключает режим. Pipeline API и CLI согласованы;
   прежний Web-вызов сохраняет семантику ошибок.
4. Неравномерная запись даёт долю времени, отличную от доли records; явные паузы
   исключены одинаково из числителя и знаменателя без двойного вычитания.
5. Missing/invalidated/непригодные anchors не увеличивают покрытие; переход через
   missing run и длинный интервал двух наблюдений не считаются наблюдаемым GPS.
6. Пограничные интервалы относительно `maximum_observed_gps_interval_seconds`,
   полностью missing FIT, единственный record, нулевое активное время, ошибочные
   timestamps, неоднозначный timer и корректный финальный stop проверены отдельно.
7. Endpoint inputs и реконструкция не меняют исходную coverage; при отказе gate
   не вызываются routing/acquisition/DEM и не создаётся corrected FIT.
8. Без endpoints восстанавливается допустимый internal gap; prefix/suffix остаются
   unresolved, независимо от близости исходного начала и конца.
9. Только start восстанавливает только prefix; только finish — только suffix;
   обе точки допускают оба края. Правдоподобные сохранённые края не меняются.
10. Одно кольцо с общей точкой и сохранённой серединой восстанавливает края
    независимо; нет нулевого whole-loop shortcut. Проверяется несовместимый ввод.
11. Missing prefix/suffix с близкими кандидатами использует approximate policy;
    invalidated/mixed не получает её обходом proof/selection. Недоказанный сбой
    начала не отбрасывается лишь из-за указанного старта.
12. Ошибочная далёкая точка, unsafe FIT context, continuity boundary, OSM coverage
    failure, физически невозможное время и неудачный snapping дают локальный отказ.
13. Распределение по signals/active time учитывает паузы. DEM полезен при наличии
    evidence; отсутствие DEM не ломает допустимую 2D-реконструкцию.
14. Partial reconstruction проходит composed writer preflight, round-trip FIT read,
    validation и diff; timestamps, исходные preserved coordinates, sensors и
    неизвестные/developer fields сохраняются согласно прежнему writer contract.
15. Повтор с теми же входами, конфигурацией и snapshots даёт тот же выбор и audit
    за исключением явно operational duration fields.
16. Pipeline/CLI smoke: один FIT, FIT с точками, FIT+GPX; внутренние JSON/HTML отчёты
    согласованы с планом, применёнными изменениями и FIT diff.
17. Старый формат вызова pipeline работает без новых аргументов, в том числе
    с прежними policy/config и default-вызовом. Неизменённый Web проходит свои
    существующие FIT+GPX tests; его worker, конфигурация и public schema не требуют
    миграции. Проверить последовательные FIT-only и FIT+GPX вызовы на отсутствие
    утечки настроек режима через shared state.

Coverage calculation — линейный проход с переиспользованием timeline (либо
`O(n log p)` для поиска по p паузам), без O(n²) reachability. Сохранить существующую
цель анализа ~20 000 records менее 5 секунд на современном ноутбуке; сетевые запросы
и подготовку графа измерять отдельно. Reconstruction остаётся bounded существующими
budgets; timeout публикует разрешённый partial результат и причины отказов.

Private acceptance: выбрать реальные FIT с внутренними пропусками и краями;
GPX, если есть, скрыт от pipeline и используется только для внешнего сравнения.
Синтетические fixtures обязательны независимо от доступности private файлов.
Private FIT, endpoints и производные артефакты не коммитить.

Приёмка по внутренним отчётам обязательна дополнительно к автоматическим тестам:
сохранить воспроизводимые CLI-команды, конфигурации/snapshot IDs и внутренние
JSON/HTML результаты для выбранных случаев: internal gap, prefix, suffix, одно
кольцо, отказ по coverage и partial reconstruction. Проверить на карте границы
изменений, сохранение исходных участков, соединения, распределение по времени,
причины отказов и FIT diff. Наличие сгенерированного отчёта само по себе не означает
приёмку: зафиксировать результаты его изучения и замечания в отчёте реализации.

Команды при реализации: `python -m pytest`, `python -m pytest web/tests`,
`python -m ruff check .`, `python -m mypy src`; выполнить проверки затронутых
companion packages. `web/tests` в 022 — регрессионная проверка старого Web с новым
pipeline, а не приёмка FIT-only Web. Зафиксировать фактические команды,
результаты, private skips и performance measurements в отчёте реализации.

Task завершён только после выполнения всех критериев, зелёных regression suites
и приёмки по внутренним отчётам; только затем разрешено начинать Task 023.
Подготовка этого ТЗ не означает выполнения acceptance реализации.

## 10. Вне scope и ограничения

- FIT-only Web UI/API, worker/job metadata, серверные настройки и публичные отчёты:
  отдельная [Task 023](023-fit-only-web.md) после завершения 022.
- FIT без достаточной сохранённой геометрии; поиск целого неизвестного маршрута.
- Несколько кругов, ввод промежуточных waypoints и ручной редактор маршрута.
- Пользовательские времена старта/финиша, добавление records и изменение timestamps.
- Изменение правдоподобного движения по OSM, DEM или пользовательской точке.
- Ослабление detector proof и approximate-политики для invalidated/mixed gaps.
- AI/LLM, новые поставщики карт, новый routing engine и deployment.

Качество зависит от OSM coverage, оставшейся геометрии и доступных signals.
Принятый маршрут остаётся гипотезой; отсутствие дороги в OSM или невозможность
однозначно обосновать invalidated край может оставить gap unresolved даже при 99%
исходного покрытия и заданном endpoint.
